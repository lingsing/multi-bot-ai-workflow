# 门禁规则

门禁的核心思路：**执行可以委托，判断留给人**。只在不可逆或对外可见的地方设确认点，其余步骤尽量自动化，并保证可回滚、可叫停。

示例脚本里的门禁分两层：

- **调度层**：`examples/lib/common.sh` 中的关键词门禁，在路由之前判断。
- **执行层**：追加到每条提示词末尾的执行守则 `WF_GUARD_SUFFIX`。

| # | 规则 | 门禁结果 |
|---|---|---|
| 1 | 关键选型由人决定，执行可委托 | 放行，但执行者只出对比方案 |
| 2 | 对外发消息/发布/推送前必须本人确认 | 待本人确认 |
| 3 | 一句「停」立即叫停全部，并报告已改内容 | 全部退出 |
| 4 | 修改前先备份、可验收、不改无关配置 | 执行守则约束 |
| 5 | 交易类禁止自动下单 | 拒绝（不可绕过） |
| 6 | 设计未获批不开发前端 | 拦截 |
| 7 | 监控只读不杀进程 | 只报警 |
| 8 | 未核实信息不当作事实 | 显式标注并单独列出 |

---

## 规则 1：关键选型由人决定，执行可委托

**为什么**
选型（技术栈、方案、工具）的影响是长期的，错了要整体返工；而且选型往往取决于执行者看不到的约束（个人偏好、已有资产、后续计划）。执行者擅长把候选方案的信息收集全、对比清楚，但不应该替人拍板。

**怎么检查**
- 任务描述含“选型 / 拍板 / 技术栈 / 最终方案”时，提示词追加：“只输出候选方案、对比维度与风险，不做最终决定”。
- 汇总备注中标明“涉及关键选型，执行者只出对比方案”。
- 验收时看产出是否为“对比表 + 风险”，而不是“已经按某方案实施”。

**反例**
- 让执行者“调研一下任务队列方案”，它调研完直接选了一个并开始改代码接入。
- 汇总里写“已确定使用 X”，而这个决定没有经过本人。

---

## 规则 2：对外发消息 / 发布 / 推送前必须本人确认

**为什么**
对外动作对他人可见、难以撤回：消息发出去收不回来，发布的内容可能已被看到或转载，推送的代码可能已被他人拉取。这一类动作的代价不对称——晚发几分钟几乎无损，发错一次可能代价很高。

**怎么检查**
- 任务描述含“发布 / 推送 / 发送 / 群发 / 外发 / 上线 / 发帖”及对应英文词时，`dispatch.sh` 不自动执行，记为“待本人确认”。
- 只有同时满足：`--run`、`--confirm`、交互终端、本人手动输入「确认」，才会执行。
- 非交互环境（cron、管道）一律视为未确认。
- 执行守则中写明“不对外发送、发布或推送任何内容”，防止执行者在非对外任务中自作主张。

**反例**
- 让执行者“写一段产品更新文案”，它写完顺手发到了社交平台。
- 定时任务里配置了“生成周报并发送给团队”，没有任何确认点。
- 用 `yes | ./dispatch.sh --run --confirm ...` 之类的方式自动“确认”——示例中非交互输入会被拒绝。

---

## 规则 3：一句「停」立即叫停全部，并报告已改内容

**为什么**
自动化出错时最需要的是一个简单、可靠、覆盖全部的刹车。如果叫停需要逐个找到正在跑的任务，往往来不及；叫停后如果不知道已经改了什么，就无法判断该回滚什么。

**怎么检查**
- `stop_all.sh --run` 写入 STOP 标志文件（含时间与原因）。
- 所有脚本（`dispatch.sh`、`monitor_collect.sh`、`news_relay.sh`）在**启动时**和**每一步/每条任务之前**检查 STOP 标志，存在则以退出码 3 退出。
- 叫停同时生成“已改内容报告”：最近一段时间内修改过的文件列表、仍在运行的执行者进程（只列出不结束）。
- 解除需要显式执行 `stop_all.sh --clear --run`，避免误恢复。

**反例**
- 只停了正在跑的那个任务，下一个定时任务照常启动。
- 叫停后只回复“已停止”，没说停之前已经改了哪些文件。
- 叫停开关本身也检查 STOP 标志，导致停了之后无法查看状态或解除。

---

## 规则 4：修改前先备份、可验收、不改无关配置

**为什么**
委托执行的前提是“出错可以回滚”。没有备份的修改不可回滚；没有验收方式的修改无法判断是否完成；顺手改了无关配置的修改会在别处制造难以追溯的问题。

**怎么检查**
- 每条提示词末尾追加执行守则：修改前先备份；只改与本任务相关的文件；结束时列出已改文件、验收方式、未核实项。
- 编程类任务额外要求“先备份或在新分支进行”；视频类要求“不覆盖原素材，输出到新文件”。
- `crontab.example` 明确说明手动粘贴，不用脚本覆盖已有 crontab。
- 验收时对照“已改文件”清单检查是否有任务范围之外的改动。

**反例**
- 让执行者修一个脚本的 bug，它同时“顺便”格式化了整个目录、改了编辑器配置。
- 视频剪辑直接覆盖了原始素材。
- 交付时只说“改好了”，没有说怎么验证。

---

## 规则 5：交易类禁止自动下单

**为什么**
交易直接涉及资金，后果不可逆；而新闻与分析天然包含不确定性（见规则 8）。把“分析”和“下单”之间的距离拉到最大，是这个工作流里最硬的一条线。和规则 2 不同，这里**没有“确认后自动执行”这一档**。

**怎么检查**
- 任务描述含“下单 / 买入 / 卖出 / 开仓 / 平仓 / 加仓 / 减仓 / 挂单”等词时，`dispatch.sh` 直接拒绝，任何参数都无法绕过。
- 研究接力（`news_relay.sh`）每一步提示词都写明“只分析不下单，不登录交易账户，不给出买卖指令”。
- 接力输出中若出现交易指令类词汇，只告警标注，不执行、不作为建议转发。
- 工作流中不配置任何交易账户凭据。

**反例**
- “分析今天的新闻，如果利好就自动买入”。
- 市场核对步骤为了“核对价格”登录了交易账户。
- 汇总里写“建议立即买入 X”，并被当作行动指令转发。

---

## 规则 6：设计未获批不开发前端

**为什么**
前端开发成本高、迭代快，在未定稿的设计上开发，大概率要推倒重来。先让人审设计，再投入开发。

**怎么检查**
- 编程类任务描述含“前端 / 页面 / 界面”等词时，未加 `--design-approved` 则拦截。
- 允许先做设计相关的非开发任务（如出草图、写交互说明），审批通过后再开发。

**反例**
- 只说了一句“想要一个任务看板”，执行者直接写了一整套页面。
- 设计还在讨论中，开发已经并行开始，结果设计一改全部返工。

---

## 规则 7：监控只读不杀进程

**为什么**
监控的职责是“让人知道”，不是“替人处理”。自动结束进程可能误杀正在使用的程序或正在执行的任务，造成数据丢失；而晚一点发现高负载，代价通常很小。

**怎么检查**
- `monitor_collect.sh` 只调用只读命令（macOS：macmon / top / vm_stat / sysctl / ps / df；Linux：/proc/stat / /proc/meminfo / ps / free / df）。
- 脚本内把 `kill / pkill / killall` 覆盖为报错退出，即使将来有人误加了这类调用也会立即失败。
- 超阈值只输出 `ALERT` 行并在日报中汇总，处理方式由本人决定。

**反例**
- “CPU 超过阈值就结束占用最高的进程”。
- 磁盘快满时自动删除“看起来像缓存”的目录。

## 规则 8：未核实信息不当作事实

**为什么**
多步接力会放大错误：第一步的一条未经证实的消息，经过分析步骤会变成“影响判断”，再经过汇总就可能被当成事实转述。必须在源头标注，并让标注一路传递下去。

**怎么检查**
- 调研与抓取类提示词要求每条附来源链接；无法给出可访问来源或来源相互矛盾的，标注 `[未核实]`。
- `news_relay.sh` 每一步结束后扫描输出，列出所有 `[未核实]` 行；抓取步骤中没有链接的列表项自动视为未核实。
- 分析步骤要求“只基于给出的材料，不引入新事实”，对未核实条目的结论也带 `[未核实]`。
- 汇总中单独列出未核实项，转述时必须保留标注。

**反例**
- 抓取结果里一条没有来源的传闻，经过分析后出现在汇总的“要点”里，没有任何标注。
- 分析步骤为了“补全背景”引入了材料中没有的数据，且未说明来源。

## 关键词门禁的局限

- **漏判**：换一种说法（如“分享出去”“挂上去”）可能不命中关键词。
- **误判**：如“推送通知功能的设计文档”会因“推送”被拦为待确认。

处理原则：**宁可误判，不可漏判**。误判的代价是多一次人工确认；漏判的代价可能是一次不可撤回的对外动作。执行守则作为第二道防线兜底。改进方向见 README 的路线图。
